## 2. 技术栈与目录

### 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 站点生成 | Astro 5.14 | 静态、SEO 好、组件可复用、i18n 路由原生 |
| 数据存储 | YAML + git | 可 diff、可回滚、可多人协作 |
| 校验 | 构建期 Python 脚本 | 缺来源 / 缺字段直接构建失败 |
| 交互 | 纯前端 + 预生成 JSON 索引 | 对比器和时间轴不需要后端 |
| 投稿 | GitHub Issues + 审核合入 | 有审核、无服务器、可公开追溯 |

## 3. 数据模型（整个项目的地基）

**一句话：一份带时间维度和来源的事实库 → 由字段注册表驱动渲染 → 静态输出 + 纯前端交互。**

内容先行，但对比器和时间轴不是"以后加的功能"，它们是**对数据模型现在的硬约束**。

### 3.1 实体分层

| 层 | 实体 | 说明 |
|---|---|---|
| 1 | `class` | 舰级。公共数据（设计指标、装甲方案、武备布置） |
| 2 | `ship` | 单舰。身份 + 生命周期节点 + **差异数据** |
| 3 | `fact` | 一条带时间窗和来源的数据点 |
| 4 | `narrative` | 一段有争议的叙述（多说法并列） |
| 5 | `weapon` / `image` / `battle` | 独立实体，id 互相引用 |

**fact 与 narrative 的分界**：能写成一个值 / 一个字段的是 fact；写不成字段的（"沉没原因是战损还是自沉"、"谁几点下的命令"）是 narrative。**两者都不能删掉有争议的一面。**

### 3.2 fact 的四条硬规则

```yaml
- field: displacement.standard      # 必须来自字段注册表，不许自由文本
  value: 41700
  unit: t
  src: [kbismarck-bsweights]       # 至少一个，没有来源构建直接失败
  valid: { from: 1940-08-24, to: 1941-05-27 }   # 时间窗必填
  confidence: A                     # 证据层级 A–D
  note: 德方标准排水量口径
```

1. `field` 必须来自 `data/fields.yaml`。
2. `valid` 时间窗必填——没有"永久有效"，服役前后不是一回事。
3. `src` 至少一个。
4. **同 field + 同时间窗出现多条 = 自动构成分歧**，不需要额外标记。

**第 4 条是关键：分歧不是异常情况，是数据结构里的一等公民。**

### 3.3 时间轴：拖动即变

```
candidates = facts.filter(f => f.field == F && f.valid.from <= T <= f.valid.to)
0 条 → 显示"无记录"（不是 0）
1 条 → 直接显示
N 条 → 主值 + 分歧角标 + 可展开对比
```

**为什么不用"整舰快照"**：Bismarck 服役到沉没只有 9 个月，但雷达、迷彩、编制、防空炮位都变过。每次改装存完整快照，几百艘船的数据会爆炸还必然互相漂移。**字段级时间窗 + 补丁式覆盖**是唯一可扩展的做法。

时间轴粒度按内容档位分三档：甲=逐日（150–300 条/舰，Bismarck 做到 151 条，1941-05-27 一天 32 条）、乙=关键节点+改装（30–60 条）、丙=仅重大节点（5–10 条）。

### 3.4 舰级继承与单舰覆盖（省工作量的核心机制）

**同级舰公共数据写在 class 上，单舰只写差异。**

解析顺序（同一时刻、同一字段）：
```
1. 单舰 fact（T 在时间窗内）
2. 舰级 fact（T 在时间窗内）
3. 未记载
```

单舰 fact 命中即覆盖舰级，**不与舰级值构成分歧**——覆盖是"这艘船就是这样"，分歧是"同一艘船同一指标有两种说法"。页面上自动标出「与舰级不同」的项。

**P4 的验收点**：新增一艘单舰要能只写差异字段，否则继承机制等于没做。

### 3.5 主值规则（唯一默认显示哪个）

```
1. 证据层级高者优先（A > B > C > D，E 不参与）
2. 层同：口径明确者优先（来源自己解释了定义）
3. 层同、口径同：采集时间新者优先
4. 仍平：按 source id 字母序（保证构建可复现）
```

实例：Bismarck 标准排水量显示 **43,978 t**（KBismarck，逐项累加自证口径），而非 41,700 t（英文维基，未标口径）。41,700 保留在分歧列表，角标常显。

**主值不是裁决结果，是"默认我先给你看哪个"。**

### 3.6 单位与口径

- 存储层统一公制（t / m / kn / mm），英制只在展示层换算。
- 排水量三个独立字段，**不合并**：`displacement.standard` / `displacement.full` / `displacement.deep`。
- 口径本身进字段注册表，不在正文解释。

### 3.7 两条 P1 期间新增的约定

1. **fact 可带 `about` 键**指明归属实体——`about: weapon:<id>` 走 weapon.* 字段，`about: mount:<id>` 走 mount.* 字段，缺省 = 文件主体。这样同一文件能容纳舰级 + 武器 + 炮位三种实体，不用拆目录。校验器按 `(field, about, qual, from, to)` 分桶判分歧，不同炮位同名字段不会被误判成两种说法。
2. **文件级 `open_ended_note`**——舰级文件里绝大多数参数有效期到该级全损为止，逐条写 note 纯属噪音。顶层声明一次，校验器就放过所有 `valid.to` 为空的条目。

## 7. 内容真实性原则（最重要的纪律）

### 7.1 证据层级

```
A  一手档案（战争日志、脱险报告、倾斜试验记录、官方档案）
B  同期官方出版物（Jane's 当年度卷、海军部手册）
C  权威二次文献（Conway's、Campbell、Okun 等专家论述）
D  专题网站（NavWeaps、KBismarck、combinedfleet）
E  百科与聚合内容（仅用于找线索，不作为 fact 来源）
```

E 档**不能**作为 fact 来源。校验脚本会拦。

### 7.2 分歧的处置流程

1. **先判口径冲突**：不同来源说的不是同一件事（设计值 vs 实测值 vs 敌方估算）→ 拆成不同字段并存，不做裁决。
2. **确认为真冲突** → 按证据层级择优，`note` 写明采信理由，**另一说必须保留**。
3. **无法裁决** → 并列展示，页面标"存在争议"。这本身是内容，不是缺陷。

### 7.3 绝对不做的事

**删掉有争议的说法。** 无论哪种情况，被否定的说法都要留在数据里（`note` 或 `narrative`），因为下一代研究者会重新拿它出来。删掉等于把网站的寿命锁在今天的认知水平上。

**把推断值写进前端。** 无法直接溯源到来源的值（例如测距仪数量 4/6/5）只记布尔事实（"三个指挥所圆顶：未装→装"），推算过程留在 `work/` 备查，**不进 `data/`**。

### 7.4 图片授权分档

| 档 | 条件 | 处理 |
|---|---|---|
| **A · 归档** | PD / CC0 | 下载到本地；记录机构 + 藏品号 + 许可 + 获取日 |
| **B · 外链** | CC-BY / CC-BY-SA；或授权待确认 | 只放链接与缩略图；有署名义务的强制渲染署名 |
| **C · 禁用** | IWM 全站、大和ミュージアム、Europeana NoC-NC、一切 "Editorial use only" | 不出现，连缩略图都不放 |

三条硬约束：
1. **授权跟着"这张具体的数字化副本"走，不跟着"这个历史事件"走。** 同一张 Bismarck 照片，NHHC 版是 PD、Bundesarchiv 版是 CC-BY-SA、IWM 版是非商业。归档必须记机构与藏品号。
2. **IWM 的"非商业"卡的是本站商业模式。** 条款写明一旦有广告、商品销售、订阅、placement、donation 就不再属于 allowed use。本站已定无变现，故 IWM 可作 B 档；**一旦变现必须重新评估、C 档化**。IWM 另明文禁止裁剪与转载第三方站，所以只外链原图，不做二次加工。
3. **Bundesarchiv 不得整库标 CC-BY-SA 3.0 de。** 实测官网条款页根本没这字样，CC 协议只覆盖当年与德语维基合作的那批 Bestand，逐张确认，确认不了写"需进一步确认"并只外链。

**另：** NARA Catalog API 条款禁止缓存 API 返回内容（"Please do not cache or store any content returned by the API"）。元数据不落库；PD 图片另从直链或 NHHC 站内 Download 归档，两件事分开处理。

## 8. 工作流程（怎么继续生产内容）

已经跑顺的流水线：

```
① 派 subagent 做单一主题的深度调研
   → 产出 work/raw/<topic>.md（带每个数值的英文原句 + 来源 URL + 争议标注）
② 主 agent 审阅，决定哪些进 data/、哪些进 narrative、哪些标注"未获取"
③ 改 data/*.yaml
④ python scripts/validate.py      （必须 0 错误）
⑤ python scripts/selftest.py      （29 例全过）
⑥ cmd /c "npm.cmd run dev" 本地看效果
⑦ cmd /c "npm.cmd run deploy"
```

**subagent 调研的铁律**（已经用血的教训换来的）：
- 只给主题，不给答案。任务书里的"背景"经常本身是错的，要求 subagent **每条结论带英文原句**，并能反驳任务书前提。
- 明确要求区分"未获取"和"0"。查不到就写查不到，不许推算。
- 要求登记 `src`，并对分歧单列。
- 已知多次出现：任务书给的前提错误（如"胡德 1941-05-27 沉没"实为 05-24、"1999 Ballard 考察胡德"根本不存在、"光辉级早期没弹射器"不成立）。**这是正常的，subagent 纠错比顺着写有价值。**

## 10. 已知坑（踩过，别再踩）

| 坑 | 现象 | 解法 |
|---|---|---|
| PowerShell 执行策略 | 直接敲 `npm` 报"无法加载 npm.ps1" | 一律 `cmd /c "npm.cmd run xxx"` |
| 国内连 workers.dev | curl 返回 000 超时 | 走 `http://127.0.0.1:7897` 代理 |
| NavWeaps / 德文维基直连 | TCP 443 阻断 / TLS 握手超时 | 同上，先验代理端口通不通，不通就提醒人开 SakuraCat（`D:\sakuracat\SakuraCat.exe`） |
| Wikimedia 缩略图 | `iiurlwidth=1600` 返回 400 | 只放行 120/250/330/500/960/1280/1920/3840，用 1280 或下 1920 本地缩 |
| Wikimedia 原图路径 | `/wikipedia/commons/<hash>/<file>` 301 回首页 | 正确形式是 `/wikipedia/commons/thumb/<hash>/<file>/<w>px-<file>` |
| upload.wikimedia.org | 走代理也 429 | 改用 thumb 站 |
| 中文乱码 | PowerShell 输出 GBK | 用 read 工具读文件；写 `.ps1` 要带 BOM |
| 论坛类信源 | warships1discussionboards 全卡 Cloudflare 挑战页 | 换源，别硬刚 |
| 部分专业站 | kbismarck 两页之间数据自相矛盾 | 逐条标源，别当成一个权威整体 |

## 12. 给下一个接手的人

**你想继续这个项目，按这个顺序：**

1. 读 `docs/00-framework.md`（401 行）—— 所有设计决策的原始理由都在里面，比这份文档权威。
2. 看 `data/classes/bismarck.yaml` 的结构——那是打过样的标准。
3. 跑一次 `python scripts/validate.py`，确认现在是绿的。
4. 想加新舰？先派 subagent 按 §8 的规矩做调研，产出 `work/raw/xxx-tech.md`，再照 `ships/tirpitz.yaml` 的形状写数据。
5. 改完必跑 validate + selftest，再 deploy。

**这个项目最容易被做坏的地方：**
- 为了赶进度把"查不到"写成推测值。**这网站的整个价值建立在"每条数据都能点开看来源"上**，一破就全破。
- 为了页面好看把有争议的说法删掉。同理。
- 把 B 档图（CC-BY-SA）当 A 档塞进 `public/img/`。上线前必须逐张核 license。

**用户的沟通习惯**（影响交付方式）：
- 要结论先给，但要能追到推导。
- 大工程先报价（token/时间）再动手。
- 他会在看到效果后改需求，需求变更是常态，不是返工。
