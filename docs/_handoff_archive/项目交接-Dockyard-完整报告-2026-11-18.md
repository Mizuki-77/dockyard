## 2. 三条红线（违反即废掉整个项目的价值）

### 2.1 有争议的说法一条都不删

被否定的说法要留在 `note` 或进 `narrative`，因为下一代研究者会重新拿它出来。删掉等于把网站的寿命锁在今天的认知水平上。

**实践中怎么落地**：两个来源打架就两条都留，`note` 里写「两说并列，不裁决」。例：
- 胡德号 Type 284 装成日：协会记 03-15、年表记 03-17，本站取 03-17 作起点（理由是不把没装完的时段算作已装），但两个日期都写在正文里。
- 38 cm SK C/34 射速三说、14 in 北角海战弹数、g7a 装药 280 vs 430 kg、525 in 仰角 70° vs 80°、UP 火箭座数 3 vs 4……

### 2.2 推断值不进 `data/`

无法直接溯源到来源的值，只记可溯源的布尔事实；推算过程留 `work/`。

**实践中怎么落地**：
- 雷达功率、频率、波长、探测距离——素材里零星有（FuMO 23 有 368 MHz / 9 kW / 25,000 m），但 `fields.yaml` 没有对应字段，所以**一条都没写进 fact**，只在 `note` 里说明「注册表无对应字段，不入库」。
- 33 个雷达/火控/舰载机实体**全都没有 `weapon.in_service_from`**——不是漏了，是查不到型号首服役年。
- `37mm-sk-c30` 射速有 30 / 80 / 40 三说，索性一个数字都不写。

### 2.3 fact 的 `field` 必须在注册表里；`valid` 时间窗 + 至少一个 `src` 必填

缺任何一项，`validate.py` 直接报错。`src` 引用的 id 必须在 `sources.yaml` 登记过，且 **tier E（百科）不能作 fact 来源**。

## 3. 数据模型（整个项目的地基）

### 3.1 实体分层

| 层 | 实体 | 说明 |
|---|---|---|
| 1 | `class` | 舰级。公共数据（设计指标、装甲方案、武备布置） |
| 2 | `ship` | 单舰。身份 + 生命周期节点 + **差异数据** |
| 3 | `fact` | 一条带时间窗和来源的数据点 |
| 4 | `narrative` | 一段有争议的叙述（多说法并列） |
| 5 | `weapon` / `mount` / `image` / `battle` | 独立实体，id 互相引用 |

**fact 与 narrative 的分界**：能写成一个值 / 一个字段的是 fact；写不成字段的（「沉没原因是战损还是自沉」「谁几点下的命令」）是 narrative。

### 3.2 fact 的骨架

```yaml
- field: displacement.standard      # 必须来自 data/fields.yaml
  value: 41700
  unit: t
  src: [kbismarck-bsweights]        # 至少一个，必须已登记
  valid: { from: 1940-08-24, to: 1941-05-27 }   # 时间窗必填
  confidence: A                     # A / B / C
  note: 德方标准排水量口径
  about: weapon:38cm-sk-c34         # 可选：指明归属实体
  qual: { shell_type: apc }         # 可选：限定词
```

**同 field + 同时间窗出现多条 = 自动构成分歧**，不需要额外标记。**分歧不是异常情况，是数据结构里的一等公民。**

### 3.3 舰级继承与单舰覆盖

**同级舰公共数据写在 class 上，单舰只写差异。** 解析顺序（同一时刻、同一字段）：

```
1. 单舰 fact（T 在时间窗内）
2. 舰级 fact（T 在时间窗内）
3. 未记载
```

单舰 fact 命中即覆盖舰级，**不与舰级值构成分歧**——覆盖是「这艘船就是这样」，分歧是「同一艘船同一指标有两种说法」。页面上自动标出「与舰级不同」的项。

**P4 的验收点**：新增一艘单舰要能只写差异字段，否则继承机制等于没做。**这个机制已被验证**（提尔皮茨、KGV、光辉号三艘都是这么入库的）。

### 3.4 主值规则（唯一默认显示哪个）

```
1. 证据层级高者优先（A > B > C > D，E 不参与）
2. 层同：口径明确者优先（来源自己解释了定义）
3. 层同、口径同：采集时间新者优先
4. 仍平：按 source id 字母序（保证构建可复现）
```

主值**不是裁决结果**，是「默认我先给你看哪个」。

### 3.5 证据层级

| 档 | 内容 | 能否作 fact src |
|---|---|---|
| A | 一手档案（战争日志、脱险报告、倾斜试验记录） | ✅ |
| B | 同期官方出版物（Jane's 当年度卷、海军部手册） | ✅ |
| C | 权威二次文献（Conway's、Campbell、Gunston） | ✅ |
| D | 专题网站（NavWeaps、KBismarck、navypedia） | ✅ |
| E | 百科（维基） | ❌ **只能找线索** |

### 3.6 单位与口径

- 存储层统一公制（t / m / kn / mm），英制只在展示层换算。
- 排水量三个独立字段，**不合并**：`displacement.standard` / `.full` / `.deep`。
- `rejected_units` 里有 `mt` / `tonne` / `lt` / `st` / `ft`——写了会报错并给换算提示。

### 3.7 两条 P1 期间新增的约定

1. **fact 可带 `about` 键**指明归属实体——`about: weapon:<id>` 走 `weapon.*` 字段，`about: mount:<id>` 走 `mount.*` 字段，缺省 = 文件主体。校验器按 `(field, about, qual, from, to)` 分桶判分歧，不同炮位同名字段不会被误判成两种说法。
2. **文件级 `open_ended_note`**——舰级文件里绝大多数参数有效期到该级全损为止，逐条写 note 纯属噪音。顶层声明一次，校验器就放过所有 `valid.to` 为空的条目。

### 5.4 `/battles` 海战历史 —— **三层树**

```
海区 → 年份 → 战斗
```

- 第一层为什么是海区：读者来找「俾斯麦最后那几天」时，记得的是「北大西洋」，不是「1941 年」
- 年份单独成层：同一片海里一年可能有七八场护航战，年份能单独折叠才收得住
- 跨年战斗**按 `date.from` 归，只出现一次**——在两年下各出现一次会让「1942 年有几场」虚高

## 6. 本轮新增的机制（最容易被后人改坏的部分）

### 6.1 `src/lib/catalog.ts` —— 本站分类表

**为什么单独成文件、为什么不进 `data/`**：
「主炮 / 副炮 / 防空炮」不是史料里的字段，是**本站给模型制作者做的检索分类**。皇家海军自己的文件里叫 `secondary armament` 或 `HA/LA mounting`，没有「role」栏。写成 fact 就等于把本站的推断塞进数据层，违反红线 §2.2。

`data/` 只留 `weapon.category`（naval_gun / anti_aircraft_gun / torpedo / rocket / radar / fire_control / aircraft / other，这是有出处的粗类），`catalog.ts` 负责把「粗类 + 型号」映射成树上的位置。

**判据不是「历史上怎么叫」，是「模型制作者会把它放在模型哪个部位」**：一个 10.5 cm SK C/33 的模型件属于上层建筑两侧的高炮平台，所以进「防空炮」而不是「副炮」，哪怕它同时承担对舰任务。

页面明确标注「分类：本站归并」。

### 6.2 `src/lib/tree.ts` —— 左树装配

两套建树逻辑原先在 4 个页面各写一遍（武器列表页 / 武器详情页 / 海战列表页 / 海战详情页），加一层得改 4 处。现在收成两份：

- `buildWeaponTree(all: WeaponSummary[]): RoleNode[]` —— 类别 → 国别 → 型号
- `buildBattleTree(battles, opNameOf): TheaterNode[]` —— 海区 → 年份 → 战斗

**一件武器可能有多个 nation 时，它在每个国别下都会出现一次**。这是有意的：读者按国别找东西时，不该因为「主国别不是这个」就找不到它。

### 6.3 切片配图（`sliceImages()`，在 `data.ts`）

用户明确要求「时间条拖动时，每个阶段下面都要有一张图」。实现是**自动匹配**，不靠手工给 36 个切片逐一配图：

| 优先级 | 规则 | `how` 标记 |
|---|---|---|
| 1 | 切片里显式写了 `image: <id>` | `explicit` |
| 2 | 照片 `date` 落在切片时间窗内（primary → A 档 → 距窗起点最近） | `in_range` |
| 3 | 窗外最近一张，且间隔 **≤ 365 天** | `nearest` |
| 4 | 都没有 | `none` → 页面显示「该时期无影像」 |

**阈值为什么是 365 天**：初版设 3 年，实测把 KGV 1942 年切片挂上了 1945-08 日本投降的合影——那两天舰上多了一整套雷达和防空平台，外形差得远。宁可不显示，也不要让模型制作者照着错的照片改模型。

**日期标签只到年 / 月时按区间处理**：`"1941"` 在字典序上小于 `"1941-05"`，直接比字符串会把全年的图判掉。

**切片没图时显式隐藏大图**，不能留着上一片的老图（否则读者会以为 1955 年退役时舰还是 1940 年那个样子）。

当前覆盖率：俾斯麦 7/7、提尔皮茨 7/7、KGV 8/8、胡德 5/5、光照 8/9（缺 1955 年退役拆解那片，Commons 上确实没有）。

### 6.4 `theater` 字段

`BattleFile.theater` —— 海区枚举（`atlantic` / `north_sea` / `mediterranean` / `indian_ocean` / `pacific` / `arctic` / `baltic` / `other`）。

## 7. 图片体系与授权

### 7.1 授权三档

| 档 | 条件 | 处理 |
|---|---|---|
| **A · 归档** | PD / CC0 | 下载到本地；记录机构 + 藏品号 + 许可 + 获取日 |
| **B · 外链** | CC-BY / CC-BY-SA；或授权待确认 | 只放链接与缩略图；有署名义务的强制渲染署名 |
| **C · 禁用** | IWM 全站、大和ミュージアム、Europeana NoC-NC、一切 "Editorial use only" | 不出现，连缩略图都不放 |

### 7.2 三条硬约束

1. **授权跟着「这张具体的数字化副本」走，不跟着「这个历史事件」走。** 同一张 Bismarck 照片，NHHC 版是 PD、Bundesarchiv 版是 CC-BY-SA、IWM 版是非商业。归档必须记机构与藏品号。
2. **IWM 的「非商业」卡的是本站商业模式。** 本站已定**无广告、无打赏、无周边**（2026-11-17 用户拍板），故 IWM 可作 B 档；**一旦变现必须重新评估、C 档化**。IWM 另明文禁止裁剪与转载第三方站，所以只外链原图。
3. **Bundesarchiv 不得整库标 CC-BY-SA 3.0 de。** 实测官网条款页没这字样，CC 协议只覆盖当年与德语维基合作的那批 Bestand。

### 7.3 IWM 判例（2026-11-18 定）

**这个判例消解了一个真实冲突**：`§5.4` 硬约束 1 说「授权跟副本走」，而早期调研笔记说「Commons 上有 IWM 的图本身就说明是违规上传」（因为 IWM 禁止 upload to third party sites）。

| 情况 | 档位 | 理由 |
|---|---|---|
| 原件藏 IWM、Commons 副本标 Public domain（Crown Copyright 已过期、无署名义务） | **A · 归档** | 授权跟副本走；作品本身已无版权，IWM 条款约束的是它对外供给的渠道 |
| 从 IWM 站内直接下载的副本 | **B · 外链** | 受 IWM Non-Commercial Licence 约束 |
| Commons 上无 PD 依据 / 署名要求 non-commercial | **C · 禁用** | 不赌 |

**A 档归档时 `note` 必须写 IWM 编号 + 出处说明。** 判例写在 `data/images.yaml` 头部与 `docs/00-framework.md §5.4`。

**残留风险（已知）**：Commons 的 PD 标签是社区标注不是法律担保；`FL 2425`、`A 29571` 这两张的 Commons `Credit` 直接指向 `media.iwm.org.uk`，即上传者取自 IWM 站内。一旦发现误标，撤图改外链。

### 7.5 图片来源的技术要点

- **缩略图宽度只允许** 120 / 250 / 330 / 500 / 960 / 1280 / 1920 / 3840。本站习惯 1280。用 `iiurlwidth` 缩略节点，不要用 unscaled 原图路径（会 429）。
- Commons API：`/w/api.php?action=query&titles=File:XXX&prop=imageinfo&iiprop=url|size|extmetadata&iiurlwidth=1280&format=json`
- 落盘后**用 Pillow 实测像素**写进 `width`/`height`，不要照抄源图尺寸。
- 国内**必须**走代理 `http://127.0.0.1:7897`。

## 8. 工作流程（怎么继续生产内容）

### 8.1 已跑顺的流水线

```
① 派 subagent 做单一主题的深度调研
   → 产出 work/raw/<topic>.md（带每个数值的英文原句 + 来源 URL + 争议标注）
② 主 agent 审阅，决定哪些进 data/、哪些进 narrative、哪些标「未获取」
③ 改 data/*.yaml
④ python scripts/validate.py      （必须 0 错误）
⑤ python scripts/selftest.py      （29 例全过）
⑥ cmd /c "npm.cmd run dev" 本地看效果
⑦ cmd /c "npm.cmd run deploy"
```

### 8.2 subagent 调研的铁律（血泪换来的）

- **只给主题，不给答案。** 任务书里的「背景」经常本身是错的，要求 subagent **每条结论带英文原句**，并能反驳任务书前提。
- **明确要求区分「未获取」和「0」。** 查不到就写查不到，不许推算。
- **要求登记 `src`，并对分歧单列。**
- 已知多次出现任务书前提错误（「胡德 1941-05-27 沉没」实为 05-24、「1999 Ballard 考察胡德」根本不存在、「光辉级早期没弹射器」不成立）。**这是正常的，subagent 纠错比顺着写有价值。**

### 8.3 并发 subagent 的写文件冲突（本轮踩到的）

多个 subagent 同时写同一个大文件会互相覆盖。**解法**：让每个 agent 写**独立分片**（如 `work/imgfrag/img-radar.yaml`），主会话用脚本合并。

合并脚本 `work/merge_imgs.py` 的设计值得沿用：
- **不用 `yaml.dump` 重写整个文件**——`images.yaml` 顶部有 10 行授权规则与 IWM 判例注释，`yaml.dump` 会全丢。
- 只做文本追加，逐条序列化成块式映射。
- **必须给含 `: ` 的值加引号**，否则 `ScannerError: mapping values are not allowed here`。
- 幂等：`existing` 与 `existing_files` 双查重。

### 8.4 新增一艘单舰的步骤

1. 派 subagent 按 §8.2 的规矩做调研，产出 `work/raw/xxx-tech.md`
2. 照 `data/ships/tirpitz.yaml` 的形状写 `data/ships/<id>.yaml`（**只写差异字段**）
3. 舰级公共数据写到 `data/classes/<class>.yaml`
4. 切片写 `data/slices/<id>.yaml`
5. 正文写 `data/articles/<id>.yaml`（结构照 `tirpitz.yaml`）
6. 配图：Commons 找图 → 落 `public/img/ships/` → 登记 `data/images.yaml`
7. 跑 validate + build

## 10. 环境与命令（Windows 专用坑）

### 10.1 命令

```powershell
cmd /c "npm.cmd run dev"        # 本地开发 :4321
python scripts/validate.py      # 全量校验（数据 + 舰艇正文 + 武器正文）
python scripts/validate.py --ship illustrious   # 只查单舰（不含武器正文）
python scripts/selftest.py      # 29 例自测
cmd /c "npm.cmd run build"
cmd /c "npm.cmd run deploy"     # 需先开代理
```

> **PowerShell 里必须走 `npm.cmd`**，直接敲 `npm` 会撞执行策略（`npm.ps1` 被禁）。

### 10.2 本轮踩到的坑（按痛感排序）

1. **YAML 流式映射写 title 会静默坏数据。** `title: { zh: ..., en: ..., 1939 }` —— `en` 句子里的逗号被当成键值分隔符，后半句变成垃圾键。有 15 条这么坏的，而且是「解析成功」的坏（不报错，只多一个 `1939: null` 键）。**给 subagent 的范本必须用块式 title。**
2. **`yaml.dump` 会丢文件头注释。** 合并大 YAML 只能用文本追加，且必须给含 `: ` 的值加引号。
3. **Vite 文件监听会崩。** 用脚本批量改 `data/*.yaml` 时报 `EBUSY: resource busy or locked, watch '...tmp'`，dev server 整个挂掉。已在 `astro.config.mjs` 的 `watch.ignored` 里加了 `**/*.tmp` 与 `**/*.bak*`，但偶发仍会崩——**遇到就重启 `npm run dev`**。
4. **dev server 会锁 `data/` 与 `src/` 的文件句柄**，导致 `edit`/`write` 报 `ReplaceFileW EIO (Win32 32)`。**先停 dev 再改**；同一文件连续两次失败就说明是占用，**不要重试第三次**。
5. **PowerShell 里 `python -c "..."` 带中文或嵌套引号极易被拆碎**（报 `+ CategoryInfo : ObjectNotFound: (tl:String)`）。**超过两行的 python 一律写成 `work/*.py` 文件再跑。**
6. **Chrome headless 截图输出路径不能含空格。** 项目路径是 `D:\deepseek harness\...`，会报「系统找不到指定的路径 (0x3)」。先写 `$env:TEMP\` 再拷回来。脚本：`work/shoot.ps1 -Pages 'a','b' -W 1440`。
7. **PowerShell 输出中文是 GBK 乱码。** 用 read 工具读文件，别信控制台回显。需要看 python 输出就读 `.txt`。
8. **PowerShell 的 `[id]` 会被当通配符。** 处理 `src/pages/*/[id].astro` 这类路径要用 python 或 `-LiteralPath`。
9. **`git` 在本机不可用。** 批量改文件用 python 脚本，先 `assert s.count(old) == 1` 再替换。
10. **`upload.wikimedia.org` 对本站持续 429**，且只接受档位宽度。用 `thumb.wikimedia.org/.../{N}px-...` 是唯一稳的路。

### 10.3 网络

- 国内直连 `workers.dev`、NavWeaps（443 阻断）、de.wiki（TLS 握手超时）、Wikimedia 都不通。
