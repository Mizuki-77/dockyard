# 战舰资料站 · 总体框架（v0.2 草案）

> 状态：讨论稿，v0.2 已吸收四项决策，待最终确认后进 P0。
> 定位：二战战列舰/巡洋舰为主，现代舰次之，一战舰再次。
> 双重用户：历史爱好者（要战史、行动记录）+ 模型制作者（要部位细节、涂装、时间点状态）。

---

## 1. 一句话架构

**一份带时间维度和来源的事实库 → 由字段注册表驱动渲染 → 静态输出站点 + 纯前端交互。**

内容先行，但对比器和时间轴不是"以后加的功能"，它们是**对数据模型的硬约束**，必须现在满足。

---

## 2. 模块结构

```
舰船资料      舰级 → 单舰（只写差异）→ 状态切片
武器与装备    火炮/炮塔/鱼雷/雷达/火控，独立实体，多舰复用
图片与线图    按舰 / 按部位 / 按时间 三套索引
海战史        战役 → 参战舰只（双向链接）
模型制作      套件库 / 涂装方案 / 部位细节图 / 改造参考
数据溯源      每条数据可点开：来源、分歧、采信理由
工具（后置）  舰船对比器、时间轴浏览器、穿深查询
```

模型制作模块的检索轴是**部位**，不是**舰**。这是与其他资料站的主要差异点。

---

## 3. 数据模型

### 3.1 实体分层

| 层 | 实体 | 说明 |
|---|---|---|
| 1 | `class` | 舰级。舰级公共数据（设计指标、装甲方案、武备布置） |
| 2 | `ship` | 单舰。身份信息 + 生命周期节点 + **差异数据** |
| 3 | `fact` | 一条带时间窗和来源的数据点 |
| 4 | `narrative` | 一段有争议的叙述（多种说法并列），见 3.8 |
| 5 | `weapon` / `image` / `battle` | 独立实体，用 id 互相引用 |

第 1、2 层之间是**继承 + 覆盖**关系，见 3.6。这是控制工作量的核心机制。

**fact 与 narrative 的分界**：能写成一个值的是 fact，能写成一个字段的是 fact。写不成字段的——"沉没原因是战损还是自沉"、"谁在几点下的命令"——是 narrative。**两者都不能删掉有争议的一面**，见 3.8。

### 3.2 核心：fact（事实记录）

**所有会变的、有争议的数据，都存成 fact，而不是直接写在舰艇对象上。**

```yaml
- field: displacement.standard
  value: 41700
  unit: t
  src: [kbismarck-bsweights]
  valid: { from: 1940-08-24, to: 1941-05-27 }
  confidence: A
  note: 德方标准排水量口径
```

四条硬规则：

1. **`field` 必须来自字段注册表**——不允许自由文本字段名。
2. **`valid` 时间窗必填**——没有"永久有效"的字段，服役前的值和服役后的值不是一回事。
3. **`src` 至少一个**——没有来源的 fact 构建直接失败。
4. **同 field + 同时间窗出现多条 = 自动构成分歧**，不需要额外标记位。

第 4 条是关键：分歧不是异常情况，是数据结构里的一等公民。

### 3.3 时间轴（拖动即变）

查询时刻 T 的某字段：

```
candidates = facts.filter(f => f.field == F && f.valid.from <= T <= f.valid.to)
0 条  → 未记载（显示"无记录"，不是 0）
1 条  → 直接显示
N 条  → 主值 + 分歧角标 + 可展开对比
```

**主值选取规则（写死，见 3.9）**：证据层级高者优先 → 层同则口径明确者优先 → 再同则采集时间新者优先。**主值只是默认显示值，不是"正确答案"**；其余值一律保留，可展开，且角标常显。

**为什么不用"整舰快照"**：Bismarck 从服役到沉没只有 9 个月，但雷达、迷彩、编制、防空炮位都变过。若每次改装存一份完整快照，几百艘船的数据会爆炸且必然互相漂移。**字段级时间窗 + 补丁式覆盖**是唯一可扩展的做法。

**时间轴的粒度也分档**（与 3.7 的内容档位对应）：

| 档 | 时间轴粒度 | 典型条目量 |
|---|---|---|
| 甲 | 逐日，重要日子逐小时 | 150–300 条 / 舰 |
| 乙 | 关键节点 + 改装 | 30–60 条 / 舰 |
| 丙 | 仅重大节点（下水、服役、战沉） | 5–10 条 / 舰 |

Bismarck 按甲档做到了 151 条（1941-05-27 一天 32 条）。**粒度是内容档位的函数，不是统一标准。**

### 3.4 字段注册表（对比器的地基）

```yaml
# data/fields.yaml
- id: displacement.standard
  label: { zh: 标准排水量, en: Standard displacement }
  type: number
  unit: t
  group: 尺寸与排水
  compare: true
  better: none        # none | higher | lower | context

- id: speed.max
  label: { zh: 最大航速 }
  type: number
  unit: kn
  group: 动力
  compare: true
  better: higher
```

对比器 = 取两艘舰、遍历 `compare: true` 的字段、各自解析主值、表格渲染。**不需要为每对舰艇写任何定制代码。**

`better: context` 用于装甲厚度这类"不是越厚越好"的字段（布置方式、倾角同样重要），渲染时不做高低着色。

### 3.5 单位与口径

- **存储层统一公制**（t / m / kn / mm），英制在展示层换算。
- 排水量口径必须显式区分：`displacement.standard` / `displacement.full` / `displacement.deep` — 三个独立字段，**不合并**。
- 口径本身也是字段元数据的一部分，进注册表，不在正文里解释。

### 3.6 舰级继承与单舰覆盖（省工作量的关键）

**同级舰的公共数据写在 class 上，单舰只写差异。**

```yaml
# classes/bismarck.yaml —— 舰级公共数据
class: Bismarck
facts:
  - field: displacement.standard
    value: 41700
    src: [kbismarck-bsweights]
```

```yaml
# ships/bismarck.yaml —— 单舰：只写差异，不加 facts 键就完全继承
class: bismarck
id: bismarck
launched: 1939-02-14
```

```yaml
# ships/tirpitz.yaml —— 单舰：大部分继承，只标不同点
class: bismarck
id: tirpitz
launched: 1939-04-01
facts:
  - field: displacement.standard
    value: 42900                       # 改装后增重，覆盖舰级值
    src: [kbismarck-tirpitz]
```

**解析顺序**（同一时刻 T、同一字段）：

```
1. 单舰 fact（T 在时间窗内）
2. 舰级 fact（T 在时间窗内）
3. 未记载
```

单舰 fact 命中即覆盖舰级，**不与舰级值构成分歧**——覆盖是"这艘船就是这样"，分歧是"同一艘船同一个指标有两种说法"，两件事不能混。若确实要标注差异，用 `inherits: false` 显式声明。

页面上自动标出「与舰级不同」的项，这正是你要的"合并同类项、展现不同之处"——**差异本身自动生成，不用手写对比**。例如 Tirpitz 页会自动高亮排水量、航速、防空武备与其他同级舰的差异。

### 3.7 内容优先级（决定铺开顺序）

**主力舰 + 历史上重要的舰艇做单舰档案；其余按舰级档案 + 代表舰。**

| 档 | 范围 | 粒度 |
|---|---|---|
| 甲 | 战列舰、战列巡洋舰、重巡洋舰、航空母舰 | 单舰，逐艘展开 |
| 乙 | 轻巡洋舰、驱逐舰领舰、大型潜艇 | 舰级档案 + 重要单舰展开 |
| 丙 | 驱逐舰、潜艇、护卫舰等 | 舰级档案，单舰仅列名与结局 |
| 丁 | 现代舰 | 按现役主力逐艘，历史舰按乙档 |

"重要"的判定标准（写死，避免每次争论）：参与过著名海战 / 有标志性技术突破 / 有重大战损或战果 / 模型套件丰富。满足任一条即升档展开。

### 3.8 narrative（叙述性争议）

fact 装不下这类东西："沉没原因是战损还是自沉"不是一个字段的值，是一场仍在进行的辩论。

```yaml
# narratives/bismarck.yaml
- id: bismarck-sinking-cause
  question: { zh: Bismarck 因何沉没？, en: Why did Bismarck sink? }
  positions:
    - id: battle-damage
      claim: { zh: 战斗损伤导致不可控进水 }
      held_by: [Mearns]
      evidence: 英军 2,800+ 发炮弹、400+ 命中，加鱼雷
    - id: scuttling
      claim: { zh: 舰员自行凿沉 }
      held_by: [Oels, Ballard]
      evidence: 09:30 下令自沉，约 10:20 装药爆炸；Ballard "Bismarck did not implode"
    - id: both
      claim: { zh: 两者皆是——炮火必然致沉，自沉加速结局 }
      held_by: [Cameron, Dulin, Garzke, Jurens]
      evidence: 2002 年考察原话 "BOTH!!"，学界主流
  status: disputed        # disputed | settled | minority
  current_consensus: both
```

规则：

1. **所有说法都列，一个都不删**，包括官方口径。德国 1941-05-27 国防军公告只说"成为优势兵力之牺牲品"、完全未提自沉——这条也要留，因为它是史料的一部分，能说明当时的宣传口径。
2. `held_by` 写主张者，不写"有人认为"。**没有署名的观点不进 narrative。**
3. `current_consensus` 标主流但不作为结论——页面同时显示主流与少数说。
4. 能降到 fact 的争议就降：排水量不是 narrative（拆字段即可），沉没原因只能是 narrative。

页面渲染：默认折叠，标题旁标"存在争议（N 种说法）"。**不默认展开**——它不该抢走读者第一眼看到的数据，但必须一眼可见、一键可达。

### 3.9 主值规则（唯一默认显示的取值）

同一字段在同一时刻有多个候选值时：

```
1. 证据层级高者优先      A > B > C > D，E 不参与（见 5.2）
2. 层同：口径明确者优先   来源自己解释了定义（如"按 1922 华盛顿条约逐项累加"）> 未解释
3. 层同、口径同：采集时间新者优先
4. 仍平：按 source id 字母序（保证构建可复现，不随机）
```

实例：Bismarck 标准排水量显示 **43,978 t**（KBismarck，逐项累加自证口径）而非 41,700 t（英文维基，未标口径）。41,700 保留在分歧列表里，角标常显。

**主值不是裁决结果**，是"默认我先给你看哪个"。读者点开就能看到全部。

## 4. 多语言

**中英双语，用户可切换；元数据一律英文。**

```
字段名、单位、枚举值  → 英文，不翻译（displacement.standard / kn / sunk-by-scuttling）
标签与正文            → zh + en 两份
拿不准的译名          → 保留原文，不硬译
```

```yaml
label: { zh: 标准排水量, en: Standard displacement }
term:  { zh: Scharnhorst, en: Scharnhorst }     # 舰名不译，两栏同值
term:  { zh: 通商破坏战, en: Handelskrieg }      # 德文原词保留，中文给意译
```

规则：
- **舰名、人名、装备型号不翻译**，中英文都写原名（Bismarck / ビスマルク / «Бисмарк» 仅在必要时加转写）。
- **拿不准的中文译名留英文**，并在 `term_note` 里写"暂无通行中文译名"，不自己造词。宁可不译，不可乱译。
- 正文允许一侧缺失：只有 zh 时，英文界面回退显示 zh 并标注"EN translation pending"。**不阻塞施工**。

## 5. 来源与可信度体系

### 5.1 来源登记表

```yaml
# data/sources.yaml
- id: kbismarck-bsweights
  title: Bismarck Weights & Measures
  url: https://www.kbismarck.com/bsweights.html
  type: specialist-site
  tier: C
  fetched: 2026-11-17
  license: 引用，不转载
```

### 5.2 证据层级

```
A  一手档案（战争日志、脱险报告、倾斜试验记录、官方档案）
B  同期官方出版物（Jane's 当年度卷、海军部手册）
C  权威二次文献（Conway's、Campbell、Okun 等专家论述）
D  专题网站（NavWeaps、KBismarck、combinedfleet）
E  百科与聚合内容（仅用于找线索，不作为 fact 来源）
```

### 5.3 分歧的处置流程

1. **先判口径冲突**：不同来源说的不是同一件事（设计值 vs 实测值 vs 敌方估算）→ 拆成不同字段并存，不做裁决。
2. **确认为真冲突** → 按证据层级择优，`note` 写明采信理由，**但另一说必须保留**（用 3.9 决定谁做默认值）。
3. **无法裁决** → 并列展示，页面上明确标注"存在争议"。这本身是内容，不是缺陷。

**绝对不做的事：删掉有争议的说法。** 无论哪种情况，被否定的说法都要留在数据里（`note` 或 `narrative`），因为下一代研究者会重新拿它出来。删掉等于把网站的寿命锁在今天的认知水平上。

### 5.4 图片授权分档（依据 2026-11-17 调研，见 `work/raw/image-sources.md`）

| 档 | 条件 | 处理 |
|---|---|---|
| **A · 归档** | PD / CC0 | 下载到本地；记录机构 + 藏品号 + 许可 + 获取日 |
| **B · 外链** | CC-BY / CC-BY-SA；或授权待确认 | 只放链接与缩略图；有署名义务的强制渲染署名 |
| **C · 禁用** | IWM 全站、大和ミュージアム、Europeana NoC-NC、一切 "Editorial use only" | 不出现，连缩略图都不放 |

三条硬约束：

1. **授权跟着"这张具体的数字化副本"走，不跟着"这个历史事件"走。** 同一张 Bismarck 照片，NHHC 版是 PD、Bundesarchiv 版是 CC-BY-SA、IWM 版是非商业。归档必须记机构与藏品号，不能只记文件名。
2. **IWM 的"非商业"卡的是本站商业模式。** 条款写明：网站一旦有广告、商品销售、订阅、placement、donation 就不再属于 allowed use。**本站已决定无广告、无打赏、无周边**（2026-11-17 用户确认），因此 IWM 可作 B 档外链；**一旦将来引入任何变现，必须重新评估，C 档化。** IWM 另明文禁止裁剪与转载到第三方站，所以只外链原图，不做二次加工。
3. **Bundesarchiv 不得整库标 CC-BY-SA 3.0 de。** 实测其官网条款页无此字样。CC 协议只覆盖当年与德语维基合作的那批 Bestand，**逐张确认，确认不了写"需进一步确认"并只外链**。

**IWM 判例（2026-11-18 定，用于消解「C 档禁用 IWM 全站」与「授权跟副本走」的冲突）：**

| 情况 | 档位 | 理由 |
|---|---|---|
| 原件藏 IWM、Commons 副本标 Public domain（战时官方摄影，Crown Copyright 已过期） | **A · 归档** | 授权跟副本走；作品本身已无版权，IWM 条款约束的是它对外的供给渠道，不是已过期作品的复制 |
| 从 IWM 站内直接下载的副本 | **B · 外链** | 受 IWM Non-Commercial Licence 约束，不可转载 |
| Commons 上找不到 PD 依据 / 署名要求为 non-commercial 的 IWM 件 | **C · 禁用** | 授权待确认的一律不赌 |

A 档归档时 note 必须写 IWM 编号 + 出处说明。已有的 bismarck（CS 159、ZZZ 3130C）、illustrious（FL 2425、A 9793、A 29571）条目都按此判例处理。**Commons 的 PD 标签是社区标注，不是担保**（见 §4.3 第 4 条）——一旦发现误标，撤图改外链。

另：**NARA Catalog API 条款禁止缓存 API 返回内容**（"Please do not cache or store any content returned by the API"）。元数据不落库；PD 图片另从直链或 NHHC 站内 Download 获取归档，两件事分开处理。

## 6. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 站点生成 | Astro | 静态、SEO 好、组件可复用、i18n 路由原生支持 |
| 数据存储 | YAML，git 版本管理 | 可 diff、可回滚、可多人协作 |
| 校验 | 构建期 schema 校验脚本 | 缺来源/缺字段直接构建失败 |
| 交互 | 纯前端，预生成 JSON 索引 | 对比器和时间轴不需要后端 |
| 投稿 | GitHub Issues + 审核后合入 | 有审核、无服务器、投稿可公开追溯 |
| 托管 | Cloudflare Pages | 免费、CDN 快 |

**B 方案不等于需要数据库。** 对比器、时间轴、查询都在浏览器里跑，站点保持纯静态，成本和维护量差一个数量级。

### 6.1 用户纠错流程（带审核，无后端）

```
读者发现错误
  → 点页面上的「报告错误」按钮
  → 自动带出：舰船 id、字段 id、当前值、来源、页面 URL
  → 跳转 GitHub Issue（模板自动预填）
  → 你审核：采纳 → 改 YAML 并关单；驳回 → 说明理由留档
```

要点：
- **每个数据点旁边都有纠错入口**，而不是全站一个"联系我们"。带上下文的投稿质量高一个数量级。
- **Issue 本身成为溯源记录**——"这个值为什么改了"永久可查，比私下改 YAML 强。
- 一期用 GitHub 原生 Issue，不写投稿表单；等量大了再考虑表单。**完全不需要服务器**。

## 7. 路线图

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| P0 | 来源登记表 + 字段注册表 + schema + 校验脚本 | 校验能拦住缺来源的 fact |
| P1 | Bismarck 全字段打样，含状态切片 | 拖动时间轴能正确显示数据变化 |
| P2 | 站点骨架：舰级页 / 单舰页 / 图片页 / 战役页 | 一个完整链路可访问 |
| P3 | 对比器 | 任选两舰可对比，无需定制代码 |
| P4 | 横向扩展：Tirpitz（验证继承机制）→ 同舰级其他舰 → 其他舰级 → 其他国家 | 新增一艘单舰只写差异字段 |
| P5 | 纠错入口 + 图片归档 | 每个数据点可报告错误 |

P0 不通过，后面全是返工。P4 的验收点特别重要——**新增一艘单舰要能只写差异字段**，否则继承机制等于没做。

**P1 实际交付状态（2026-11-17）**：

P1 期间在数据模型上新增的两条约定（已写进文件头注释）：

1. **fact 可带 `about` 键**指明归属实体——`about: weapon:<id>` 走 weapon.* 字段，`about: mount:<id>` 走 mount.* 字段，缺省 = 文件主体。这是同一文件容纳舰级 + 武器 + 炮位三种实体的方式，不需要拆目录。校验器按 `(field, about, qual, from, to)` 分桶判分歧，不同炮位的同名字段不会被误判成两种说法。
2. **文件级 `open_ended_note`**——舰级文件里绝大多数参数有效期到该级全损为止，逐条写 note 纯属噪音。顶层写一次声明，校验器就放过所有 `valid.to` 为空的条目。

## 10. 附：代理与网络

NavWeaps 与德文维基在本机**直连不通**（navweaps TCP 443 阻断、de.wiki TLS 握手超时），但经 **`http://127.0.0.1:7897`**（SakuraCat 本地代理）两者均正常返回 200。

用法：

```powershell
curl.exe -x http://127.0.0.1:7897 -s -o NUL -w "%{http_code}" https://www.navweaps.com/...
```

**SakuraCat 需手动开启**（`D:\sakuracat\SakuraCat.exe`，监听 7897）。批量抓取前先验端口，不通就先提醒用户开代理，不要直接跑。
